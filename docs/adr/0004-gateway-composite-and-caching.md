# ADR 0004: Розширення API Gateway — Складений запит, кешування та Rate Limiting

**Статус:** Прийнято  
**Дата:** 2026-11-02  
**Контекст:** Лабораторна робота №3 курсу з мікросервісної архітектури.

---

## 1. Контекст та проблема
У попередніх лабораторних роботах (ЛР0, ЛР1, ЛР2) шлюз `ApiGateway` виконував виключно функцію зворотного проксі (Reverse Proxy) через Ocelot. 
Клієнтський застосунок для відображення одного екрана (наприклад, картки гри в магазині) був змушений робити кілька окремих послідовних запитів:
1. Запит до `CatalogService` за даними гри (назва, опис, ціна, категорія).
2. Запит до `OrderingService` для перевірки, чи придбав уже поточний користувач цю гру і який статус замовлення.

Це створювало проблеми:
- **Підвищена затримка (Network Latency):** клієнт робить кілька мережевих запитів замість одного.
- **Підвищене навантаження на базу:** повторювані запити на читання незмінних публічних даних гри щоразу йшли до БД каталогу.
- **Ризик перевантаження та DoS:** відсутність лімітів на частоту запитів (особливо на форму входу).

---

## 2. Обґрунтування вибору екрана (Composite Endpoint)
Згідно з методичними рекомендаціями (п. 3.1) було обрано **«Екран деталей об'єкта»**:
- **Маршрут шлюзу:** `GET /api/v1/store/game-details/{id}`
- **Сервіси-учасники:**
  1. `CatalogService` (`GET /api/v1/catalog/items/{id}`) — основна сутність.
  2. `OrderingService` (`GET /api/v1/orders/game-status/{id}`) — операційний статус користувача.

### Чому саме цей екран:
1. **Типовий бізнес-сценарій інтернет-магазину ігор:** користувач відкриває сторінку гри, і UI повинен одночасно показати опис/ціну гри та динамічну кнопку: «Купити» (якщо гри немає) або «Вже у вашій бібліотеці / Завантажити» (якщо є активне або завершене замовлення).
2. **Чітке розділення відповідальності:** шлюз володіє власним контрактом `GameStoreDetailsDto`, адаптованим під потреби UI, без розмивання бізнес-правил між сервісами.
3. **Паралельне виконання через `Task.WhenAll`:** виклики до обох сервісів ініціюються одночасно. Загальний час очікування дорівнює $\max(T_{cat}, T_{ord})$, а не їх сумі.

---

## 3. Таймаути та свідома деградація (Graceful Degradation)
- **Таймаут:** для викликів шлюзу встановлено жорсткий таймаут **2 секунди**.
- **Стратегія деградації:**
  - `CatalogService` є критичним: якщо він недоступний або перевищив таймаут $\rightarrow$ шлюз повертає `503 Service Unavailable` / `504 Gateway Timeout` у форматі `ProblemDetails`.
  - `OrderingService` є другорядним: якщо він недоступний $\rightarrow$ шлюз повертає `200 OK` з даними гри, а поле `userStatus` свідомо маркується як `isAvailable: false` із повідомленням `Сервіс замовлень тимчасово недоступний`.

---

## 4. Стратегія кешування (In-Memory Cache)
1. **Кешуються тільки спільні публічні дані:**
   - Деталі гри (`catalog:item:{id}`)
   - Списки ігор (`catalog:http:{path}:{query}`)
2. **Персональні дані НЕ кешуються:**
   - Замовлення, кошик, профіль, дані користувача.
3. **TTL:** 60 секунд (баланс актуальності цін та розвантаження сервісу).
4. **Інвалідизація:** при успішних мутаціях (`POST`, `PUT`, `DELETE` на каталог) шлюз миттєво очищає збережені ключі каталогу.

---

## 5. Обмеження частоти запитів (Rate Limiting)
Використано `Microsoft.AspNetCore.RateLimiting`:
- `/api/v1/auth/login`: `FixedWindow`, 5 запитів/хв за IP (захист від brute force).
- Авторизовані користувачі: `SlidingWindow`, 60 запитів/хв за `userId`.
- Анонімні користувачі: `SlidingWindow`, 20 запитів/хв за IP.
- Відповідь при перевищенні: `429 Too Many Requests` із заголовком `Retry-After: 60` та тілом `ProblemDetails`.
