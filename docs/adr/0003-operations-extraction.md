# ADR-0003. Винесення операційного сервісу (OrderingService)

## Статус
Прийнято

## Контекст
У ЛР0 та ЛР1 було винесено сервіси автентифікації (`AuthService`, порт 5001) та каталогу ігор (`CatalogService`, порт 5002).
Головною бізнес-дією предметної області NovaGames є придбання/замовлення ігор користувачем (checkout, створення замовлення, перегляд історії замовлень, скасування).
Ця дія змінює стан системи, створює фінансові транзакції, потребує гарантій цілісності та ідемпотентності, а також звертається до каталогу для перевірки наявності та актуальної ціни гри.

## Таблиця «Наші дані / Чужі дані» (розділ 4.1)

| Група | Сутності / Дані | Рішення |
| :--- | :--- | :--- |
| **Наші дані (пишемо й читаємо)** | `Order`, `OrderItem`, `IdempotencyRecord` | Переносимо у власну БД `miniproject_ordering` |
| **Чужі дані (тільки читаємо)** | `Game` (Title, Price, Discount) | Не переносимо. Запитуємо у `CatalogService` через HTTP/gRPC. Фіксуємо денормалізований `ItemSnapshot` (назва та ціна на момент оформлення) |
| **Чужі дані (ідентифікація)** | `User` (UserId, Email) | Не переносимо. Ідентифікатор користувача витягується з JWT-токена (`ClaimTypes.NameIdentifier`) |
| **Спільна технічна дрібниця** | Перелічення статусів замовлення (`OrderStatus`) | Зберігаємо як рядок (`HasConversion<string>()`) у своїй БД |

## Обґрунтування вибору
Виносимо сервіс **OrderingService**, оскільки:
1. Він володіє таблицями `Orders` та `OrderItems`, які більше нікому не потрібні на запис.
2. Він змінює стан системи (створення замовлення, зміна статусу, скасування), на відміну від суто читальних сервісів.
3. Він активно взаємодіє з `CatalogService` для валідації ігор та цін, що реалізує повноцінний міжсервісний виклик із дедлайнами та обробкою відмов.

## Архітектурні рішення
1. **База даних**: Окрема база даних `miniproject_ordering` на порту MySQL. Жодних спільних транзакцій та Foreign Key між базами.
2. **Незмінність історії (ItemSnapshot)**: У кожній позиції замовлення зберігається `ItemSnapshot` (фіксація назви та ціни на момент покупки). Навіть якщо адмін змінить ціну гри в каталозі чи видалить її, чек користувача залишиться історично достовірним.
3. **Ідемпотентність**: Реалізовано через заголовок `Idempotency-Key`. Повторний запит із тим самим ключем повертає раніше створене замовлення без дублювання записів у БД.
4. **Міжсервісна стійкість**: Виклики до `CatalogService` виконуються з обмеженням за часом (дедлайн 2 секунди) та коректно обробляють випадки: товар не знайдено (404), каталог недоступний (503 Service Unavailable), таймаут запиту (504 Gateway Timeout).
5. **Тестування**: Інтеграційні тести на базі `WebApplicationFactory` із підміною клієнта каталогу стабом/моком.

## Наслідки
+ Повна автономність процесу замовлення та історії купівель.
+ Захист від збоїв: недоступність інших частин моноліту не блокує перегляд історії замовлень.
- Необхідність обробки мережевих помилок при зверненні до каталогу (компенсується таймаутами та дедлайнами).
