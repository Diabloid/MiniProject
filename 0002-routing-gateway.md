# ADR-0002. Спосіб маршрутизації зовнішніх запитів

## Статус
Accepted (2026-09-11)

## Контекст
Монолітний застосунок NovaGames.API працює на порту 5042 і наразі обробляє всі запити самостійно. Оскільки планується винесення Auth та Catalog у процесі декомпозиції, клієнтські застосунки потребують єдиної точки входу, щоб не змінювати свої налаштування при кожному переміщенні ендпоінтів. Змінювати код самого моноліту заборонено.

## Розглянуті варіанти
1. **Без шлюзу.** Клієнт зберігає адреси всіх застосунків. Кожне винесення сервісу вимагає оновлення клієнта і ламає його роботу під час переходу.
2. **Хмарний шлюз (AWS API Gateway / Azure API Management).** Потужно, але вимагає розгортання в хмарі, що виходить за межі навчального локального проєкту.
3. **YARP (Yet Another Reverse Proxy).** Від Microsoft, дуже гнучкий і швидкий, але маршрутизація налаштовується переважно через код, що збільшує складність підтримки.
4. **Ocelot.** Легкий шлюз, де маршрути, ліміти та авторизація конфігуруються виключно через JSON-файл.

## Рішення
Обрано **Ocelot**. Його декларативна конфігурація через `ocelot.json` дозволяє перемикати маршрути без перезбирання коду. Функціоналу Ocelot цілком достатньо для реалізації патерну Strangler Fig у рамках навчального проєкту.

## Наслідки
+ Клієнт отримує єдину незмінну адресу для всіх запитів.
+ Перенаправлення трафіку на нові мікросервіси виконується зміною одного файлу.
- З'являється ще один процес (ApiGateway), який необхідно запускати і моніторити.
- Усі запити роблять додатковий мережевий крок, що додає затримку (latency) у 2-5 мс.
- Єдина точка відмови: якщо Ocelot впаде, доступ до всієї системи NovaGames буде втрачено.
