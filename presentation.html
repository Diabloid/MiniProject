Цифрова дистрибуція ігор NovaGames

Міграція монолітного інтернет-магазину на мікросервісну архітектуру

📌 Про проєкт

Повномасштабна декомпозиція системи за патерном Strangler Fig із забезпеченням автономності сервісів, ізоляції баз даних та єдиної точки входу.

🛠 Технологічний стек

  • Бекенд: .NET 10, C#, ASP.NET Core
  • Шлюз: Ocelot API Gateway (Порт 5000)
  • Бази даних: MySQL 8.0 (Database-per-Service)
  • Клієнт: WPF Desktop (.NET 10)
  • Тести: 20/20 тестів (xUnit, Moq, Integration)

Вихідний моноліт та передумови декомпозиції

Чому ми вирішили розділити монолітну систему?

🏛 Що було (Моноліт на 5042)

  • Усі модулі в єдиному процесі;
  • Спільна база novagames_monolith;
  • Жорсткі Foreign Keys між користувачами, іграми та чеками замовлень.

⚠️ Проблеми моноліту

  • Single Point of Failure: Падіння модуля оформлення чи аналітики блокувало весь магазин;
  • Нерівномірне навантаження: Каталог переглядають 95%, купують 5% — масштабувати доводилося все разом;
  • High Coupling: Будь-яка зміна схеми БД могла зламати сусідній функціонал.

Цільова мікросервісна архітектура

Топологія системи та ізоляція відповідальності

  • Ocelot API Gateway (5000): Single Entry Point, маршрутизація, Rate Limiting, Composite API, Response Cache.
  • AuthService (5001): Автентифікація, випуск JWT Access/Refresh токенів, перевірка ролей. Власна БД miniproject_auth.
  • CatalogService (5002): Каталог ігор, серверна пагінація IQueryable, фільтри. БД miniproject_catalog.
  • OrderingService (5003): Замовлення, генерація ключів, ідемпотентність. БД miniproject_ordering.
  • WPF Desktop Client: Спілкується виключно з портом 5000 і не знає внутрішньої топології.
Слайд 4 / 8

Стратегія міграції — Патерн Strangler Fig

Поетапне заміщення функціоналу моноліту без простоїв

  • ЛР0: Встановлення Ocelot API Gateway як зворотного проксі перед монолітом.
  • ЛР1 (Auth + Catalog): Винесення авторизації та каталогу в окремі сервіси. Автономна перевірка JWT без запитів до бази.
  • ЛР2 (Ordering): Відокремлення замовлень, розрив спільних FK у базі, міграція замовлень, Idempotency-Key.
  • ЛР3 (Розширення Gateway): Композитний ендпоінт для деталей гри (паралельний запит), кеш каталогу, Rate Limiting.
  • ЛР4 (Клієнтський шар): Впровадження AuthHandler у WPF UI, обробка 429 Retry-After, оновлення 5 екранів.

Найважче архітектурне рішення

Розподілена узгодженість без Foreign Keys та транзакцій

🧩 Виклик

У моноліті покупка — це одна SQL-транзакція. У мікросервісах дві фізичні БД: catalog та ordering. Потрібно гарантувати, що кошти не спишуться двічі при розриві зв'язку.

💡 Наше рішення

  • Ідемпотентність: Клієнт генерує заголовок Idempotency-Key (GUID). Повторний клік чи повтор запиту повертає існуючий чек;
  • Знімок ціни (Snapshot): Збереження UnitPrice на момент покупки, що захищає чеки від зміни цін у каталозі;
  • Композитний API: Шлюз паралельно агрегує Catalog + Ordering і підтримує часткову деградацію.

Що реально працює, а що є компромісом

Об'єктивна оцінка реалізованого рішення

✔ Працює на 100%

  • Наскрізний ланцюжок від логіну до оформлення;
  • Кешування каталогу (In-Memory з метриками);
  • Rate Limiter на логіні (5 req/min, 429);
  • Усі 20 автоматичних тестів зелені.

⚙ Технічні компроміси

  • Синхронний HTTP замість брокера: Для Enterprise краще використати RabbitMQ/Kafka для event-driven зв'язку;
  • In-Memory замість Redis: При масштабуванні шлюзу потрібен спільний розподілений кеш;
  • Відсутність Saga Orchestrator: Компенсаційні транзакції виконуються прямими викликами.

Що змінилося в логіці бекенду

Порівняння архітектурних підходів

1. Автономна валідація JWT (Zero Trust до клієнта)

Сервіси Catalog та Ordering перевіряють підпис токена локально за відкритим/секретним ключем з бібліотеки Shared. Жодних мережевих запитів до AuthService!

2. Розрив Foreign Keys та Snapshotting

У базі замовлень немає зовнішніх ключів на ігри. Зберігається числовий GameId та історична ціна покупки.

3. Ідемпотентність замість блокувань у БД

Захист від подвійних платежів реалізовано через унікальний клієнтський ключ Idempotency-Key.
